## 2 · ⚠ 发现的问题

### F1【中·真算错】`消耗 token` 卡把推理 token 又加了一遍，多报 12,872,208（+47.1%）

* 实现：`webui.html` 7788 / 7794 —— `totalTokens = s.tokens + s.think_tokens` → DOM 显示 `40.2M`。
* **数据证据（我手扫全部 28,512 行）**：`think_tokens>0` 的 **16,529** 行里，
  `think > tokens` 的 **0 行**、`tokens > think` 的 16,498 行、`tokens == think` 的 31 行。
  **零反例 ⇒ `think_tokens` 落在 `tokens` 之内，不是与它并列的第二项。**
* **代码证据**：`internal/wire/usage.go` 从 `completion_tokens_details.reasoning_tokens`（OpenAI 规范里它是
  `completion_tokens` 的**细分**）与 `completion_thinking_tokens` 取 ThinkTokens；
  单测 `usage_test.go:318/338` 的报文就是 `completion_tokens:200` + `reasoning_tokens:150`（150 ⊆ 200）；
  `internal/cline/cline.go:203` 注释原话：「代价是**思考 token 计入 completion_tokens**」。
* **后果**：日志里的 `tokens` = `usage.completion_tokens`（已含推理）。于是「输出 token 27.3M」与
  「消耗 token 40.2M」不是两个口径的量，而是**同一个量算了一遍又加了一遍**：40,186,774 − 27,314,566 = 12,872,208
  ⇒ **虚高 47.13%**。
* **一致的口径只有两种**：① 消耗 = 输出 = `tokens`（27.3M）；② 消耗 = `tokens`、输出 = `tokens − think`
  （14.4M）。现在这版两个卡语义重叠，**至少有一个是错的**。
* ⚠ 保留意见：日志不存原始 usage 报文，我无法用一条真实上游报文 100% 定案；但「16,529 行零反例 + 字段名语义
  + 单测 fixture + 源码注释」四条同向。

### F2【中·口径与文案不符】7d 趋势的「逐日」桶按 **UTC 日**对齐（本地 08:00），且窗口比「最近 7 天」多 21.38 小时

* 实测桶边界：首桶 `2026-10-10T08:00:00+08:00`、末桶 `2026-10-17T08:00:00+08:00`、步长 24h ⇒ **桶起点固定在本地 08:00**，
  不是本地零点。原因：Go `time.Truncate(24h)` 以 **UTC 零时**为基准，+08:00 时区下截断就落在本地 08:00。
* `internal/admin/series.go:32` 注释写「桶按**本地时区**对齐」—— 对小时桶成立（整点时区偏移），**对天桶不成立**。
* 后果 1：**桶数 8 而非 7**，覆盖 `2026-10-10T08:00 → 现在` = **189.38 小时（7.89 天）**，比 caption 的
  「最近 7 天」多 **21.38 小时**（`start = now.Add(-7d).Truncate(24h)` 被往前拉了一整天）。
* 后果 2：caption 写「最新 **10-17** 08:00 · 请求 6307」，而该桶实际是「**10-17 08:00 → 10-18 05:2x**」的残桶
  （含今天的数据）。用户会把「最新」读成「最新数据是昨天」。
* 24h 侧同类但轻微：**桶数 25、覆盖 24.38 小时**（同为 `Truncate` 把起点前拉）。

### F3【低·会误读，非算错】Top 榜同一行里用了**两个不同分母**

* 条宽 `width = n / 榜首值`（#1 = 100% 满格），占比 `pct = n / Σ全量54账号`（#1 = 4.1%）。
* 两者各自都对，但**并排放在一行**时，「4.1% + 满格条」很容易被读成「占 100%」；8 行占比之和 **30.8%**，
  而环形图图例之和是 **100.0%** ⇒ 同一屏右侧 100%、左侧 30.8%，看起来像算错（其实是因为榜只显示前 8 / 共 54）。
* 缓解：标题旁有 `共 54 个账号有请求`。建议：条宽也按全量归一，或把占比改成「占 Top8 的百分比」并写清口径。

### F4【低·已知口径】环心 28,512 与 Top 榜占比分母 **差 1**

* `by_uid` 跳过 1 条空 uid 行（`uid=""`），`by_provider` 把它算进 provider 桶 ⇒ 并排两个面板的「总量」差 1。
  `admin.go:2845` 有注释说明这是刻意的；我确认差 1 的来源就是那 1 行（手扫：空 uid 行 = 1）。

### F5【信息级·精度】成功率卡是整数取整

* 真实 85.6762% → 显示 `86%`（+0.32pp）；占比保留 1 位小数（如 4.12%→`4.1%`）。属显示精度分层，不是算错，
  但若有人拿卡片数字做二次计算会有 0.3pp 级偏差。

### F6【信息级】`webui.html:7770` 那行 `totalTokens` 是死代码

* 与 7788 行重复计算同一公式，但该值在 `renderStats` 里未被使用（卡片走 `statsCardsEntries`）。不影响数字，只影响后续维护者判断「到底哪处在算口径」。

## 3 · 我是怎么排除「看着对其实错」的（方法，不是"感觉一致"）

1. **先冻窗口，再谈比对**：日志是活的（10 秒 +4 行）。我不比「页面 vs 现在的日志」，而是复制一份冻结件，

   我读到的是它的 `file.path=./data-7864/request-log.jsonl`、`total=0`，该份数据被我**作废重做**）。
2. **证明"页面读的文件" == "我比的文件"**：`OpenSink` 启动会 `Prune()` 重写文件（tmp+rename，会重新序列化），
   所以我冻结了**两份**（一份给服务读、一份给脚本读），事后比对**三份哈希逐字节相同**（`A9078E63…`）
   ⇒ 排除"服务端把旧行裁掉了/字段被删了"这类静默偏差。
3. **排除"是不是缓存/时序"**：DOM 读完之后**再取一次** `/admin/stats`，`(total, tokens, think)` 三元组完全相同
   ⇒ 期间窗口未变，页面显示的与我算的是同一帧（`statsCacheTTL` 5s 缓存也在窗口内）。
4. **排除"我们俩都算错"**：除了别人写的 `verify_stats.py`，我再写一份**独立手扫脚本**（不同代码路径），
   并逐键比对 54 个 uid（不是只比 Top N）；不一致的那个键是 `(无 uid 字段)`，我追到源头是「空 uid 行」这一条，属命名差异而非计数差异。

   DOM 的 `window._statsCache` 原始字段 + 接口 JSON + 手扫整数**三路整数比对**；环形占比则直接解析
   `conic-gradient` 的四段百分比（3 位小数），与按精确值算的占比**逐段比到 0.002pp**。
6. **排除"排序看起来降序"**：不只读文本，而是把 8 行的 `tval` 全部取回按数值判严格递减，并校验
   `title` 里的全值与 `by_uid` 的键**逐个相等**（防止"值对但配错账号"）。
7. **文案不被"看着像"骗**：caption 的「最新 …」我是用 `series` 末桶的 `ts/total/ok` **自己拼一遍**再逐字比较（两条都逐字相同）。
