# 缓存更新策略设计：分层 TTL + 三触发 + 全局预算

> 用户 2026-10-18 的要求（原话）：
> "我希望缓存的更新要么是到用的时候自动返回数据更新，要么就是怎么设置时间定时更新，
> 或者懒加载，但是又要保证性能，**不能一直发请求更新**，怎么权衡比较好你设计一下"

本文回答那个"权衡"。⚠ 结论一句话：

**每份数据带上「它什么时候被读到的」，用分层 TTL 判定过期；过期才刷，且只允许三种触发方式
（读到时 / 定时兜底 / 事件驱动）去刷，全部刷动作共用一个全局预算。**

---

## 0. 先划清三层，别混为一谈

本仓同时存在三种"缓存"，它们的失效特征**完全不同**，用一套 TTL 是错的：

| 层 | 东西 | 存在哪 | 失效原因 | 谁在读 |
|---|---|---|---|---|
| A | 面板行（tasks / invite） | 服务端 `auths/loomy/panels.json` + 内存 | 上游状态变了 | 前端打开面板 |
| B | 账号池额度（quota） | 服务端 `data/state.json` | 调用消耗、上游发放 | 账号池页 / **选号权重** |
| C | 前端页面缓存 | 浏览器 `localStorage` | 只是**上一次渲染结果** | 前端首屏 |

⚠ **C 不是数据源，它是"上一次的画面"**。首屏毫秒靠它（同步读、零请求），
而它的内容来自 A/B 的响应 ⇒ **A/B 新鲜，C 自然新鲜**。
⚠ 所以设计只在 A/B 上做，C 保持"先画缓存、随后用响应覆盖"。

---

## 1. 核心机制：`fetchedAt` + 分层 TTL

### 1.1 每份数据必须知道"自己什么时候被读到的"

⚠ 现在 `panelRowCache` 只有一个**整体**的 `at`（整份最后一次写入时刻）。
那不够：一页里有些号是 5 分钟前查的、有些是 3 小时前查的 —— 用整体时刻判定会
要么全刷（浪费）要么全不刷（过时）。

⇒ 改成**每行**带 `FetchedAt time.Time`（`accountTasksView` / `accountInviteView` 各加一个字段，
`omitempty` 不破坏已有 JSON）。⚠ 落盘的 `panels.json` 里也一样带上 ⇒ **重启后不丢**。

### 1.2 TTL 按"变化速度"分层（这是权衡的支点）

| 数据 | TTL | 为什么是这个值 |
|---|---|---|
| B 账号池额度 | **3 分钟** | 随每次对话消耗而变；又是**选号权重**的输入 ⇒ 最需要新鲜 |
| A 任务状态 | **30 分钟** | 一天最多变 8 次（8 个任务各一次）⇒ 30 分钟内变化概率很低 |
| A 邀请码 | **6 小时** | 生成后几乎不变；绑定是用户手动动作 |
| A 其他（昵称等） | **24 小时** | 基本不变 |

⚠ 分层而不是统一，是因为**统一 TTL 必须迁就最短的那个**：
统一取 3 分钟 ⇒ 邀请码一天被白查 480 次；统一取 6 小时 ⇒ 额度永远是旧的。

## 2. 三种触发（全部"过期才刷"）

```
        ┌───────────────────────────────────────────────┐
        │  过期集合 = { 行 | now - FetchedAt > TTL(行) }  │
        └───────────────────────────────────────────────┘
             ▲                    ▲                      ▲
             │ on-read            │ 定时兜底              │ 事件驱动
        ┌────┴─────┐        ┌─────┴──────┐        ┌──────┴───────┐
        │ 读到过期值 │        │ 每 60s 扫  │        │ 号被调用 ⇒   │
        │ 先返回旧值 │        │ 过期集合   │        │ 标额度待刷   │
        │ 后台异步刷 │        │ 限量刷     │        │ (不立即发)   │
        └──────────┘        └────────────┘        └──────────────┘
```

### ① on-read（"用到时自动更新"）
用户翻到某页 ⇒ 服务端**立刻**用现有数据回（哪怕旧）⇒
**同时**把过期行丢进后台队列。
- ⚠ **关键：绝不阻塞响应** —— 用户永远不等上游；新鲜度靠"下一次看到"补齐。
- ⚠ 这与本仓已有的 `tasksCachedPage`（零上游、毫秒返回）**完全兼容**，只是多一个"顺手标记"。

### ② 定时兜底（"定时更新"）
⚠ 没有 on-read 触发时（没人开页面）过期集合不会自己变小 ⇒ 需要一个兜底：
每 `sweepEvery`（**60 秒**）扫一遍过期集合，**限批量**地刷。
- ⚠ 这是**唯一**在没人看的时候发请求的地方，所以批量必须小（见 §3）。
- ⚠ 已有实现可复用：`panelwarmup.go` 的 `sweepPanels`（并发 4 / 每轮 12 / 失败退避）。

### ③ 事件驱动（最精准的一条，但**只标记**）
账号刚被调用过 ⇒ 它的额度**一定**变了 ⇒ 标 `needQuotaRefresh[uid] = true`。
- ⚠ **不在调用路径上发请求**（那会把首字延迟拖长，正是用户早先抱怨的"首字慢"）。
- ⚠ 只标一下，由 ② 那轮或下一次 on-read 去刷。⚠ 本仓已有同形机制：
  `freePool.needUsed` / `needRecheck`（`noteUsed` 只挂标记，由 worker 节流查）。

## 3. 全局预算：把"不能一直发请求"变成硬约束

⚠ 上面三种触发叠加起来，最坏情况是"每次翻页都刷全部" ⇒ 必须有限流。
五道闸门，**全部已有先例，照抄**（AGENTS 第 8 条）：

| 闸门 | 值 | 出处 / 理由 |
|---|---|---|
| 并发上限 | **4** | 上游实测 **12 条并发就打 502** |
| 每轮限量 | **12** | `panelWarmupBatch` |
| 每号最小间隔 | **90 秒** | `freeRecheckEvery`（已有）：一次查完 90 秒内不再查 |
| 失败退避 | 指数（已有 `freeFailBackoff`） | 没有它就会"越失败越查" |
| 自适应降速 | 连续 502 ⇒ 间隔 ×2，封顶 10 分钟 | ⚠ **新增**：上游不稳时主动让路 |

⚠ 另加一条**方向性**原则：**事件驱动只标记、不触发请求**。
它决定的是"排序优先级"（谁最该被刷），而不是"要不要发请求"。

## 4. 请求量估算（这是"权衡"的量化答案）

44 个 loomy 号 × 2 个端点（tasks / 额度）= **88 个"行"**。

| 策略 | 稳定态请求量 | 新鲜度 |
|---|---|---|
| ❌ 每次调用都刷额度 | 跟调用量走（100 调用/分 ⇒ **100 请求/分**） | 实时 |
| ❌ 全部 60 秒刷一遍 | **88 请求/分**（固定，与有没有人看无关） | ≤ 60 秒 |
| ✅ **本设计**（TTL + 限量兜底） | **≈ 18 请求/分**（额度 44/3min + 任务 88/30min） | 额度 ≤ 3 分 / 任务 ≤ 30 分 |
| ✅ 无人访问时 | **≈ 0 请求/分**（TTL 内不刷） | — |

⇒ ⚠ **比"每次调用都刷"省 5 倍，比"全量定时"省 5 倍**，而新鲜度只差 ≤3 分钟 ——
**这就是那个权衡点**：额度晚 3 分钟知道，换掉 80% 的请求量；而 3 分钟对一个
"按分钟级使用"的网关完全够（选号权重也不需要秒级精度）。

## 5. 落地顺序（每步都能单独验证）

| # | 改动 | 为什么先做它 |
|---|---|---|
| 1 | 给 `accountTasksView` / `accountInviteView` 加 `FetchedAt`，落盘一起带 | 后面所有判定的基础 |
| 2 | 分层 TTL 常量 + `过期集合` 的纯函数（可单测，不打网络） | 逻辑先立住，测试先写 |
| 3 | `tasksCachedPage` / `inviteCachedPage` 里顺手"标记过期" | on-read 触发 |
| 4 | `sweepPanels` 改成"只刷过期集合"（现在是"只补没缓存的"） | 定时兜底 |
| 5 | **核心侧**额度定时刷新（`internal/admin/quota_refresh.go` 的 `refreshQuotas`） | 修 B 层"过时"的根 |
| 6 | 调用路径 `noteUsed` 式标记额度待刷（只标记） | 事件驱动 |
| 7 | 连续 502 ⇒ 自适应降速 | 上游保护 |

⚠ 前 4 步只动 `internal/loomy`（A 层），第 5 步动 `internal/admin`（B 层），
互不阻塞 —— 可以并行做，但**每步都要 `go build ./...` = 0 + 单测全绿才提交**。

## 6. 为什么不做的事（写下来免得反复讨论）

- ❌ **不用"过期值做减法"估算额度**：`gateway/quota_consumed.go` 记着教训 ——
  那样算出的数喂给**选号权重**，会让还能用的号被提前降权。
- ❌ **不在请求路径上同步等上游**：那正是用户早先抱怨的"首字慢"（1912ms 重试延迟）。
- ❌ **不追求实时**：本场景的消费者是**人和选号权重**，不是交易系统；
  "晚 3 分钟"的代价远小于"每分钟 100 次查询"的代价。
- ❌ **不统一 TTL**：见 §1.2 —— 统一必然要么浪费要么过时。
