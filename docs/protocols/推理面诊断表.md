# 推理面诊断表

> 为什么需要这份文件：phanthywork 的签名链有**五个**独立的易错点，而它们的失败表现**互相不可区分**——
> 已经出现过"改了 A 修好了 B 却以为修好了 A"的排查黑洞（2026-11-14 实测）。
> 每一条都给出「现象 → 真因 → 一条能证伪它的命令」。
>
> ⚠ 本文件**只指不抄**：所有细节以真源为准，这里不复述代码。

---

## ① 五个易错点（改签名前先读这一张）

| # | 易错点 | 真源（唯一的权威） | 写错的后果 |
|---|---|---|---|
| 1 | ~~三条 canonical 的分隔符不是同一个~~ → **★★ 2026-11-14 更正：三条全部用 LF（0x0A）**，没有"两条空格"这回事 | 真源是**官方实现** `magpie-PhanthyCode/src/proof.mjs`：`const LF="\n"`（L61）、`[DEVICE_PREFIX,...].join(LF)`（L112）、`[V1_PREFIX,...].join(LF)`（L131）、`[INFERENCE_PREFIX,...].join(LF)`（L164）；本仓落地在 `crypto.go` 的 `deviceV1Separator` / `inferenceSeparator` | **这里此前写错了，正是 2026-11-14 那次 `401 invalid_desktop_signature` 的根因**：device/v1 用了空格 ⇒ 设备注册恒失败、凭证永远拿不到 `registered_at_ms`。改成 LF 后真机注册一次通过 |
| 2 | **nonce 长度也不是同一个**：device / v1 = **18 字节**（base64url 24 字符），inference = **24 字节**（32 字符） | `crypto.go:99` / `crypto.go:105`；构造函数 `crypto.go:158`（`newDeviceNonce`）/ `crypto.go:161`（`newInferenceNonce`） | canonical 与服务端重算的串不一致 ⇒ 签名无效，且报错指不到长度 |
| 3 | **推理请求必须带 `x-phanthy-session` + `x-claude-code-session-id`**，且 inference canonical **第 10 段**与它们同值 | 生成与共用点在 `client.go:1104`（`buildProof`）；头发送在 `client.go:1053` | 缺任意一个 ⇒ **500 + 0 字节**（kong upstream-latency 9~10ms） |
| 4 | **proof 时间戳必须用服务端口径时间**（`server_time` 校准），不是裸本机时间 | 校准入口 `credential.go:353`（`applyServerTime`）、取值 `credential.go:399`（`serverNowMS`）；守卫在 `provider.go:1115` | 未校准即发推理 ⇒ **403 `request_not_authorized`**（文案却说"请更新或重新打开客户端"，完全指不到时钟） |
| 5 | **二次注册是终态冲突，不是成功**：服务端对"该账号已有第一台设备"回的是 **HTTP 200 + `reason_code`**，不是 409 | 判定出口 `client.go:687`（`ReasonCode` 字段）+ `client.go:716`（`RegisterDevice`）；熔断与状态落盘 `provider.go:972` | 当成成功 ⇒ 写 `RegisteredAtMS` ⇒ 拿一把服务端不认的 key 一路 403 ⇒ 账号进 `disabled_account`（**封号**） |

## ② 现象 → 真因对照

### 2.1 `500 Internal Error` + **响应体 0 字节** + `x-kong-upstream-latency` ≈ 9~10ms

**真因（唯一已证实的一种）**：请求头集合不完整 —— 缺 `x-phanthy-session` / `x-claude-code-session-id`。
服务端在解析阶段就把请求判成异常客户端，所以是空体 500，而不是带 error code 的 403。

> 判据的来历：同账号、同 key、同 body，唯一变量是两个 session 头。缺 → 500/0 字节；补齐 → 200。

**证伪命令**（不必连真机）：

```powershell
go test ./internal/phanthywork/ -run TestInferenceRequestCarriesSessionHeaders -count=1 -v
```

### 2.2 `403` + `{"error":{"code":"request_not_authorized"}}`（body 约 79 字节）

**三种原因，必须用单变量法区分**，不要凭猜：

| 子因 | 判据 | 证伪命令 |
|---|---|---|
| **时钟未校准** | 把同一次请求的 `x-phanthy-proof-timestamp` 改成 `server_time` 折算值即可恢复 200 | `go test ./internal/phanthywork/ -run TestUncalibratedAuthForcesTokenRenewal -count=1 -v` |
| **探测过密（冷却窗）** | 冷却 ≥30 秒后**同一条配方**恢复 200；窗口内连已知能成功的请求也 403 | 无法离线证伪 —— 见 §③ 的纪律 |
| 头值本身 | 已排除：`x-phanthy-client-source` 的 `cli` 与 `desktop` **都合法** | 见 §③ 的纪律（单变量） |

### 2.3 `403` + `{"error":{"code":"disabled_account"}}`（数据面也是它）

**真因**：账号已被封。**此时不要再改协议** —— 数据面（`/api/oauth/profile`、`/api/phanthy_code/models`）同样 403，
说明与签名无关。第一步永远是先探数据面：

```powershell
curl.exe -s -o - -w "`nHTTP=%{http_code}`n" --max-time 25 `
  -H "Authorization: Bearer <access_token>" `
  -H "X-Phanthy-Product: phanthy_code" `
  https://code.phanthy.com/api/phanthy_code/models
```

### 2.4 `401` + `invalid_desktop_signature`

**真因**：`v1` 或 device canonical 与服务端重算的串不一致。按 §① 的 #1 / #2 逐条核（分隔符、nonce 长度），
再核对用的是**哪把私钥**（identity / device / inference 是三把独立的 key，混用会得到同一个错误码）。

#### 实测记录 2026-11-14：CLI OAuth token + 派生 device key 被拒

用 `phanthy-code-cli` 的 OAuth 授权码换到 token，然后注册设备：

```
GET  /api/oauth/profile                          → 200 ✅（token 有效，拿到 account.uuid）
POST /api/oauth/desktop-installations/register   → 401 {"code":"invalid_desktop_signature"}
```

凭证里留下的状态是 `{"registration":{"last_attempt_ms":…}}` —— **既没有 `registered_at_ms`（没成功），
也没有 `conflict_at_ms`（不是 first_device_owner）**，即纯粹被签名拒了。

**已逐项排除的**（都对着真源核过，不是猜）：

| 怀疑点 | 结论 |
|---|---|
| device/v1 分隔符 | 代码是单空格，与 §① #1 一致 |
| nonce 长度 | device/v1 = 18 字节，与 §① #2 一致 |
| 私钥归属 | `signV1Canonical` 用 identity、`signDeviceCanonical` 用 device，与官方 `IDENTITY_POLICY`（`bindingSigner:"device"` / `headerSigner:"identity"`）一致 |
| body hash 被改写 | `RequestBodyForHash` 是恒等函数，`newJSONRequest` 不动 body |
| User-Agent | 发的是 `Bun/1.3.14`；`magpie-PhanthyCode/check-ua.mjs:49` 抓包记着「官方注册请求 200 时 UA 就是 Bun/1.3.14」 |

**★ 已定位并修复（同日）**：真因是 **device / v1 canonical 的段分隔符写成了空格**，而官方是 **LF**。
见 §① #1 的更正。改 `deviceV1Separator` 为 `"\n"` 后：

```
POST /api/oauth/desktop-installations/register  → [OK] 注册成功（HTTP 2xx，无 reason_code）
POST /admin/accounts/quota/refresh              → quota.remaining=6000, has_data=true
POST /ui/models/provider/refresh                → {"count":14,"source":"upstream"}
```

⇒ 设备注册一次通过、额度能读、目录 14 个模型全部拿到。

**复现要点（下次再遇到同类问题直接照这个查）**：

1. 先打 `GET /api/oauth/profile` 确认 token 有效（它只吃 Bearer、不验签，能过不代表签名对）
2. 再打 `register`。回 `invalid_desktop_signature` 就**按字节**核对三条 canonical 的分隔符
3. **401 不消耗设备配额**（服务端没建安装记录），所以"改一处、试一次"是安全的；
   真正危险的是 `200 + reason_code=first_device_owner`（那才是终态冲突）
4. 判定成功的唯一标准是**凭证里出现 `registered_at_ms`**；只有 `last_attempt_ms` 就是失败过

**接入成本提示**（2026-11-14 结论，供排期参考）：真实短信验证码拿号 + 一账号一设备不可解绑
+ 二次注册即封 + 设备身份要求三把独立密钥 —— 显著高于其它上游。

### 2.5 `401` + `desktop_installation_required`

**真因**：服务端不认识这个设备身份 —— 该 `x-desktop-installation-id` 没有有效安装记录
（账号被封、或从未注册、或设备记录已失效都会走到这里）。
⚠ 它**不能**用来判断"签名对不对"：签名错也常回这个码，所以别把它当验签 oracle。

### 2.6 注册响应 **HTTP 200** 但带 `reason_code`

**真因**：服务端**拒绝**了这台设备（常见值 `first_device_owner` = 该账号已有第一台设备）。

**处理**：必须走**终态冲突**分支（记 `ConflictAtMS` + `ReasonCode`、**不写** `RegisteredAtMS`、之后熔断不再注册）。
**继续重试 = 把账号打进 `disabled_account`。**

**证伪命令**：

```powershell
go test ./internal/phanthywork/ -run TestRegisterReasonCodeIsTerminalConflict -count=1 -v
```

## ③ 排查纪律（这批错误特有的）

### 3.1 单变量对照实验的最小间隔是 **≥30 秒**

上游对密集推理请求会进入约 **2~4 分钟**的 403 冷却窗；窗口内用**已知能成功的配方**也是 403。
实测：连续 6~8 次推理后开始 403，冷却 32~35 秒后同一请求恢复 200。

**所以**：当你"一次只改一个头"却看到全失败时，先怀疑冷却窗，再怀疑协议。
⚠ **不要为了验证这条纪律而故意打满配额** —— 它会加速账号风控。

### 3.2 先看 `x-kong-upstream-latency`，再看错误码

- **≈ 9~10ms + 0 字节** ⇒ 请求头集合不完整（§2.1）
- **20ms 以上 + 带 error code** ⇒ 已经到达业务层，是业务/鉴权判定（§2.2 起的各条）

### 3.3 一个账号只能有一台设备

**不要用"客户端正在登录的账号"去做反代**：设备私钥由客户端 Rust 侧持有且不可导出
（Tauri 命令 `sign_desktop_device_binding` / `sign_desktop_activity` / `desktop_installation_identity`），
而反代自己注册第二台设备会得到 `first_device_owner` → 封号。

> 附带一条**否证过的**错误猜想，写在这里防止重犯：
> Windows 凭据管理器里那几条 `daily-activity-ed25519-v4:<sha256(accountScope) base64url>` 是**签到**用的密钥，
> **不是** device identity。拿它签 `v1` 只会得到 `invalid_desktop_signature`。
