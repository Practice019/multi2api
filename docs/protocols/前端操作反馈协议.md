# 前端操作反馈协议（表格按钮 / 通知层 / 不漂移）

> 本协议是**踩了两次坑之后**补写的（2026-11-14）。第一次是"自造了一套通知层"，
> 第二次是"写了个永远绿的判据"。两者都不是手滑——是**协议里没有一条说清楚「新页面
> 接入通知层该怎么做、判据怎么算守住了」**，所以下一个 Agent 必然再踩一遍。

## 一、三条铁律

### A. 操作结论**不许落在行内**

因果链（2026-11-14 实测）：

```
结论文字写在行内（紧跟按钮）
  → 那一列是 width:1% + 右对齐 ⇒ 列宽随内容变化
  → 按钮被结果文字挤着左右移动
  → 用户看到「点了按钮界面动了」
```

用户原话：**"点击按钮后不要位移"**。

⇒ 结论一律走右上角通知框（铁律 B）。`min-width`（铁律 C）解决的是**另一种**位移：
按钮**自己的**文案在 idle/run 之间切换导致宽度变化。

### B. 反馈一律用**共享**通知层，不许自造浮动层

通知层的**唯一实现**是 `internal/server/toast.js`，由 `tools/toast_sync.js` 注入到
需要的页面（`PAGES` 清单）。它具备：

- 多行堆叠（批量操作一次几十条结果，逐条列出、各自计时）
- 连续同文案合并成 `×N`
- 超过上限折叠成「…还有 N 条」
- 点任意一行立刻关掉它

**自造一套的代价不是"丑"，是行为退化**：上面四条一条都没有，批量操作会退化成
「只读得到最后一条」——也就是外壳页 2026-11-01 修掉的那个老 bug。

### C. 会随状态改文案的按钮，宽度必须固定

按钮文案在 idle/run 之间切换（"重拉" → "重拉中…"、"确认删除" → "删除中…"）时，
宽度必须不变，否则**同一行的内容会被推挤**。

做法：给该按钮（或操作列）声明 `min-width`，宽度按该页**最宽的一档文案**定。

> ⚠ **不要给按钮基类加 `min-width`**：`button.gx{width:20px}` 这类小按钮存在，
> `min-width` 会盖过 `width`，把 20px 撑成 5.5em。

## 二、宿主契约（接入一个新页面时必须提供这三样）

| 必需 | 位置 | 说明 |
|---|---|---|
| `id="toast"` 容器 | 页面 HTML | `class="notice" role="log" aria-live="polite" aria-relevant="additions text" hidden` |
| `$()` 别名 | 页面 JS | `var $ = function (id) { return document.getElementById(id); };` |
| `esc(s)` | 页面 JS | 各页自带一份（实现略有差异，故 toast.js 里不重复定义） |

**首次接入的 4 步**（模型页 2026-11-14 就是这么做的）：

```text
① 在页面 HTML 里加 <div id="toast" …></div>
② 在页面 JS 里补 $() 别名（多数页面没有）
③ 把页面加进 tools/toast_sync.js 的 PAGES
④ 跑 node tools/toast_sync.js（写入）→ 页面里出现 WB2API:TOAST 标记段
```

⚠ `toast()` 内部第一句就是 `if (!el) return;` —— **容器不存在时它是静默 no-op**。
也就是说"调了 toast 但页面没提供容器"的表现是「点了没反应」，而排查方向会被引到
网络/后端上去。这正是本仓库反复吃过的亏（错误表现指不到根因），所以判据要静态拦。

## 三、实现的两条约束（照抄不许改结构）

| # | 约束 | 为什么（不是风格问题） |
|---|---|---|
| ① | 只用 `el.innerHTML` 拼字符串，**不用** `createElement`/`appendChild` | `tests/frontend/gen_busy_feedback.js` 会把这个函数抽出来跑在**假元素**上（只有 textContent/className/innerHTML/hidden），DOM API 会直接炸 |
| ② | 只引用**函数体内**的东西：队列挂在元素上（`el._lines`），上限写成函数内常量 | 模块级变量在抽出来的那份里不存在 ⇒ `ReferenceError`（第一版踩过） |

## 四、判据（每条都绑了「会失败的命令」）

| 判据 | 命令 | 抓什么 |
|---|---|---|
| 覆盖面非空 | `go test ./internal/server/ -run TestFrontendPagesWereScanned` | 页面被改名/搬走 ⇒ 判据静默失效（空匹配即失败） |
| 通知层只有一套 | `go test ./internal/server/ -run TestFrontendHasSingleNotificationLayer` | 自造浮动通知层、行内结果（`.toasts{`、`class="actres`、`actionResultEl`） |
| 宿主契约完整 | `go test ./internal/server/ -run TestToastCallersProvideHostContract` | 调 `toast()` 却没有 `id="toast"` 容器 ⇒ 静默 no-op |
| 按钮宽度固定 | `go test ./internal/server/ -run TestFrontendLoadingButtonsKeepWidth` | 会切换文案的按钮没有作用于 button 的 `min-width` |
| 模型页钩子 | `go test ./internal/server/ -run TestModelsPageHasProviderActionColumns` | 模型页与后端路由分叉（含正向 4 钩子 + 反向 5 断言） |
| 与共享层同步 | `node tools/toast_sync.js --check` | 页面里的实现与 `toast.js` 不一致 |
| 页面自有样式越界 | `node tests/frontend/verify_theme_compliance.js` | 页面自写硬编码色/圆角/字体（7 页全扫） |
| 内联 script 可解析 | `node tests/frontend/verify_inline_script_syntax.js` | 内联 script 语法坏（清单取自 webui.go 的 `//go:embed`） |

### ⚠ 判据自己的两次假绿（这份协议最该记住的部分）

`TestFrontendLoadingButtonsKeepWidth` 一共改过三版口径，前两版都**假绿**：

| 版本 | 口径 | 结果 | 为什么假绿 |
|---|---|---|---|
| v1 | `button …中…` 同一行 | **全绿**（本该红 6 页） | 多数页面把文案拼在辅助函数里（`showBusy('处理中…')`），正文里根本没有 `el('button', …, '中…')` 这样的行 |
| v2 | 页面里有 `中…` + 有 `<button` | 红 6 页（其中 2 页**误伤**） | webui.html 满屏「加载中…」是**整块表格的占位文字**、status 页的「熔断中…」在注释里——都不是按钮文案切换 |
| v3（现在） | 「把 loading 文案**赋给按钮或按钮变量**」 | 恰好红在 channels/groups/tokens | 见上面的判据表 |

⇒ 结论：**判据写完必须做反向验证**——故意造一个违规，看它是否真的红。
只证明"能抓违规"不够，还要证明"它没有悄悄失效"。

## 五、两个反例（都真实发生）

### 反例 1：模型页自造 `.toasts`

2026-11-14 我给「重拉」做反馈时自造了一套浮动通知层，而不是去用共享层。
发现途径是**手工看页面源码**（看到了 `#toast` 的 CSS 注释与 `toast.js`），
不是任何门禁——因为当时**没有一条判据能抓到它**。

⇒ 现在由 `TestFrontendHasSingleNotificationLayer` 抓。

### 反例 2：`unknown_provider` 的文案前缀挂错了名

模型页点「重拉」一个渠道型供应商（如 `csg`），返回
`{"error":{"code":"unknown_provider","message":"phanthywork: 未知的上游 id: csg"}}`。

这个端点是**通用**的（不专属 phanthywork），错误消息却带了 `phanthywork:` 前缀。
这是文案层面的挂名错误，不是协议问题——但用户看到红字会以为出了事。

⇒ 该供应商是渠道合成行、没有上游目录可拉，本来就不该给它「重拉」按钮（尚未修）。
