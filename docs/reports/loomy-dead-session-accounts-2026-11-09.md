## 2. 检测方法（可复检）

**双重判定**，避免单一接口的误报：

1. **第一轮（便宜、快）**：`GET /api/v1/points/records`（`token:` 头）
   —— 不消耗对话 token，116 个号并发 6 路约 **23 秒**扫完。
   判据：响应含 `登录已失效` ⇒ 疑似失效。
2. **第二轮（真实工作负载）**：对第一轮所有命中的号，直接打
   `POST /api/v1/chat/completions`（`Authorization: Bearer` 头，`stream:true`，`max_tokens:5`）。
   判据：仍返回 `{"code":"100002","desc":"登录已失效，请重新登录"}` ⇒ **确认失效**。

> 两个接口用的是**同一份 session**（来自 `auths/loomy/<uid>.json`），
> 头形态分别按本仓 `applyModelsAuth` / `applyChatAuth` 的约定，不是猜的。

## 5. 已执行的处置

**动作**：对上述 10 个号逐个调用
`POST /admin/accounts/{uid}/disable`，原因统一写为：

```
登录已失效（session 无效，2026-11-09 实测确认；待重新登录）
```

**结果**：10/10 返回 `HTTP 200 {"disabled":true,...}`；账号池 `loomy 116 个 / 已禁用 10 个 / 冷却 0 个`；
禁用后服务正常（对话实测返回"正常"）。

**为什么用禁用而不是等它自己恢复**：

- 禁用的号**不参与选号、也不参与"全冷却兜底"**（`pool.go` 明确：禁用的账号永不参与兜底）
  ⇒ 可立刻消除那 2.6% 的随机失败；
- 池子里仍有 **106 个可用号**，容量充足。

**⚠️ 恢复路径（重要）**：`Pool.Disable` 是**永久禁用**，而自动恢复入口
`ResetAutoDisable` 只清理"自动禁用账本拥有的禁用"，**不认人工禁用**（`ownsDisableLocked` 判定）。
因此：**重新登录之后，需要在控制台把该号「启用」一次**（或调
`POST /admin/accounts/{uid}/enable`），否则它会一直保持禁用。

## 6. 根因（为什么这类号没有被自动标记）

**loomy 的会话失效错误是「HTTP 200 + 裸 JSON（非 SSE）」**：

```
POST /api/v1/chat/completions   （注意：请求带了 stream:true）
→ {"code":"100002","desc":"登录已失效，请重新登录","trace_id":"..."}
→ HTTP = 200     耗时 ≈ 0.2s
```

而本仓的流内错误识别（`internal/wire/sse.go` 的 `inBandErrorOf`）：

1. **只扫 SSE 的 `data:` 帧** —— 这份响应是裸 JSON，**一个帧都没有** ⇒ 根本不会被调用；
2. 即使被调用，它**只认两种字段形态**（`error_code`/`error_msg`、顶层 `error`）
   —— loomy 用的是第三种 `code` + `desc` ⇒ 也不认得。

于是整条链静默：**不分类 ⇒ 不记错 ⇒ 不冷却 ⇒ 不标记 session dead ⇒ 该号一直留在轮换里**。

**旁证**：本仓的 loomy 分类器**本来就认识这个错误**
（`internal/loomy/errorclassifier.go`：`markerSessionDead = "登录已失效"` → `ErrKindSessionDead`
→ 永久禁用 + 要求人工重登），它只是**永远收不到这段正文**。

> 详细论证与四条修复方向见 `docs/reports/loomy-stream-ended-without-finish-reason.md`。

## 7. 遗留问题与建议

### 7.1 需要用户操作（止血后收尾）

1. **重新登录这 10 个号**（优先前 3 个有额度的）；
2. 重登后**手动点「启用」**（见 §5 的恢复路径说明）；
3. 建议顺手复查其它上游是否有同类情况（本报告只覆盖 loomy）。

### 7.2 建议的代码修复（**未实施**）

按性价比排序，详见技术报告 §6：

1. `inBandErrorOf` 补第三种形态 `code` + `desc`；
2. **治本**：流式响应若"一个 `data:` 帧都没有"，把整段正文交给 `classifyErr(provider, 200, body)`
   → `登录已失效` 命中 → 该号自动进 `ErrKindSessionDead`（永久禁用 + 需重登）——
   这样**这类号会自己退出轮换**，不需要人工盘点；
3. 给"200 且零帧"记一条显式日志/计数（现在只表现为 `ttfb=- tok=-`，与"客户端断开"同形，极难发现）；
4. 可选：把 `code`(100002) 保留进错误码，便于客户端区分"要重登"与"额度不足"。

### 7.3 建议的监控（可选）

- 在管理台显示"疑似失效账号数"（判据：`credits>0` 且最近 N 次请求均为 200 零帧）；
- session 可能批量过期（本次 10 个集中在 `2609…`/`2610…` 两批），
  建议定期巡检而不是等用户报障。
