# design-notes · 去掉渠道优先级（全部候选平等轮询）

用户指令（2026-11-13，原话）：「我觉得不要设置上游或者渠道优先级 **全部去掉，全部平等**」
⇒ 覆盖上一轮「只做只读诊断、不许改语义」的红线：**本轮就要改语义**。

## 0. 阶段判断（该不该走审问）

走：这是**改选路语义**（影响每次请求走哪条渠道）+ 影响数据模型语义（Priority 字段的地位）。

## 1. 热点（调用频率 × 单次成本），只审这几个

| # | 热点 | 位置 | 为什么是热点 |
|---|---|---|---|
| H1 | 候选排序（priority desc → id asc） | `channelroute/route.go:94-99` | **每次请求**都跑；它决定"谁进池" |
| H2 | 档位选取 + 档内加权 | `server/channels_forward.go:307-403`（pickCandidate / pickCandidateExcluding / candidatesOfTier） | 每次请求调用；"只有第 0 档在轮"就出在这 |
| H3 | 第二条选路（abilities/SQL 路径） | `channelstore/select.go:62-110` | 同一件事的**第二份实现**，不改就是"两处判据打架" |
| H4 | 渠道页的 priority 输入 | `server/webui-channels.html` | 用户可见的"概念入口"，留着就是继续教用户设优先级 |

热点之外（账号池侧选号、会话粘性、key 轮询）本轮**不审**：用户那句先说渠道，主脑已定"粘性优先"。

## 2. 七问（逐条，不许空话）

**Q1 能不能不做？** 不能。用户已明确否掉"靠配置就好"这条路（原话"全部去掉，全部平等"）；
而且现状是**代码语义**造成的（只有第 0 档进常规池），不是配置问题 —— 把 6 条候选的 priority 手工设成一样只是"让用户自己绕过缺陷"。

**Q2 这份工作做几次、在哪做？** 每次请求做一次，落在 **H1（排序）** 与 **H2（选取）** 两处；
H3 是同一件事的第二实现 ⇒ **必须同批改**，否则两条路径行为分叉（本仓已吃过"两处判据打架"）。

**Q3 输入输出的性质？** 输入：候选列表（渠道 + 权重 + key 状态），**已在内存**（Plan 每次查表算出来的），无 IO。
输出：一条被选中的候选。**纯内存、无锁竞争热点**（每次请求一次）。

**Q4 10x 边界？** 候选数 6 → 60：排序 O(n log n) 与一次加权抽签 O(n) 都还微不足道；
真正的边界是 **weights 全等时抽签退化成均匀分布**（正是用户要的），以及**候选数为 1**（此时不许有任何"换人"路径把它绕开）。

**Q5 失效模式？**
  1. **均匀 vs 粘性冲突**：粘性（同一会话固定走一条）会让"看起来不均匀" —— 本轮**不动粘性**（主脑已定粘性优先），
     但诊断里必须能解释"为什么这件事看起来不匀"（见 Q6/断言⑥）。
  2. **权重极端值**：weight=0/负数 ⇒ 仍按 1 处理（沿用既有口径，不许因此饿死一条候选）。
  3. **候选数为 1**：只能选它；重试时"已试过"立刻为真 ⇒ 必须**明确失败**而不是死循环。
  4. **全部候选都失败** ⇒ 用"所有候选都已试过"作为终止条件（守住"防无限重试"这条既有硬要求）。
  5. **残留配置里的 priority** ⇒ 不报错、不生效（保留字段但不读）。

**Q6 有没有更简单的？** 有，但都不够：
  · "只删 priority 排序、保留档位" ⇒ 所有候选同档 ⇒ **等价于**本轮方案，但会留下"档位"这个概念与那句"档位用尽"的错 —— 概念残留比代码残留更难清；
  · "UI 隐藏 priority" ⇒ 只藏界面，语义没变（用户下次还会问同一个问题）；
  ⚠ 所以取"**语义真的平等** + 诊断可见"，并把 `Priority` 保留成"**不读**的字段"（零迁移可回退）。

**Q7 证伪命令（怎么知道我做错了）？**

```bash
# ① 把 priority 排序加回 channelroute.Plan ⇒ 均匀覆盖断言必红
go test ./internal/server/ -run TestChannelPickUniformCoverage -count=1
# ② 把档位选选取回 pickCandidateExcluding ⇒ 同上必红
# ③ 改 channelstore.Select 的 attempt 语义 ⇒ TestSelectIgnoresPriority 必红
go test ./internal/channelstore/ -run TestSelectIgnoresPriority -count=1
```

## 3. 性能梯子

**落在 L1「别做」**：优先级档位这件事**整个不做**（每次请求少一次分档扫描 + 少一层"档位用尽"判据）。
不用更低一级（L0 改配置）的理由：用户已明确否掉；L0 也做不到"全部平等"（代码只看第 0 档）。
L6（微优化）**不做**，留给测量：抽签本身是 O(n) 的一趟累加，不是瓶颈。

## 4. 结构（code-conventions）

不新建包、不移动目录：改动全部落在既有三个文件 + 一个页面。
`channelroute` 仍是**只读的计划层**（Explain/Tally 都只读）；`server` 仍是执行层；`channelstore` 仍是存储+选路兼容层。
依赖方向不变（server → channelroute → channelstore）。

## 5. 取舍声明（写进代码注释的那几条）

1. `channelstore.Priority` **保留字段、路由不读**：删字段要迁移、风险大；保留但忽略可**零迁移回退**。
2. `Weight` **保留**（用户说的是"优先级"）：默认全 1 ⇒ 事实上完全平等；要连权重也去掉另说。
3. **会话粘性不动**（粘性=对话连贯，与轮询正交）。
4. 账号池侧选号**本轮不动**。
